## 任务 3：配音进队列、真实花费回写、画布新增节点（2026-10-02）

### 做了什么

- **配音进队列**：`POST /episodes/:id/voiceover` 的估价 / 确认 / 402 上限语义不变；`confirm:true` 改为逐镜建 `/ai-tasks`（`kind: tts`，参数带 `_vo` 回写信息），返回 `{tasks, skipped}`，任务中心里显示为“镜头 #N · 旁白配音”。worker 完成后 `packages/local/src/voiceover/queue.js` 读音频 / 词时间戳 blob，在一个事务里经内核 `recordGeneration` 写旁白版本（含词级字幕块），再物化旧列；合成期间台词或音色改过则 `STALE_INPUT` 跳过；启动时 `recoverFinished` 补写崩溃前已完成的任务（幂等）。新增 `GET /episodes/:id/voiceover/status`（逐镜 none / queued / running / failed / stale / fresh），时间线编辑器的“旁白配音”抽屉提交后每 2 秒轮询并显示“配音中：N 个排队，M 个生成中”，完成后刷新。
- **真实花费回写**：provider 结果带 `usage`（视频 `duration` + `SR`、配音 `characters`、图片张数）；`spend.actual()` 按价目换算后写 `spend_log.actual` 与 `spend_log.usage`（迁移 `28_spend_log_usage.sql`）；`summary.total` 多 `estimated / actual / actual_count`，`prices` 带 `version / date / sample`。花费页：顶部说明“费用按百炼公开价目计算（2025-12-19 版）”，合计卡显示预估合计与“实际 ¥x（已回传 a/b 个任务）”，逐任务表加“实际”“用量”列（如“5 秒 × ¥1.00（1080P）”“120 字符 × ¥0.0002”）。
- **价格表**：`packages/local/configs/prices.json` 换为百炼公开价目（2025-12-19，来源见文件 `source`）：wan2.6-t2v 0.6 元/秒（720P）/ 1.0 元/秒（1080P）、cosyvoice-v2 2 元/万字符（汉字计 2 字符）、wan2.6-t2i 0.2 元/张，这三条已核对（`verified:true`）。
- **画布**：工具栏“新增节点”（shot / script_line / image / video / narration；镜头与剧本行需选场景组，经 `canvas.addNodeAt`，新节点放在最右侧并自动选中）；未选中节点时属性面板列出场景组，可改名（新意图 `canvas.renameGroup`，去空白、非空、≤200 字）。时间线页的两个本地撤销 / 重做按钮移除，Ctrl+Z / Ctrl+Shift+Z 改为先保存未提交编辑再走内核历史（与顶栏撤销同一份）。

### 观察项处理（同日第二轮，win/testing）

1. 时间线页重复提示：已修。`apps/renderer/src/api/timelines.js` 的 `getByEpisode` 改为 `silentError`——404 是“尚未组装”的正常态，`TimelineEditor.vue` 本来就有“该剧集尚未组装时间线”的空态引导，两次弹窗来自请求拦截器在首次加载和 `views.revision` 监听重载时各弹一次。测试 `apps/renderer/test/timelineApi.test.js`（断言只有 getByEpisode 静默，assemble/save/addClip/patchClip 照常报错）。
2. 开发态 better-sqlite3 ABI：根因是提升式 node_modules 里只有一份 `better_sqlite3.node`，`pnpm install` 装的是 Node 25（NODE_MODULE_VERSION 141）的预编译包，Electron 39 要 140，谁刚重编过另一边就起不来（第二轮复现时正好反过来：二进制是 140，`pnpm dev` 能起但 `packages/local` 测试加载失败）。处理：`scripts/native-abi.mjs <node|electron>` 负责切换并在目标运行时里真的 require 一次；根 package.json 加 `native:node` / `native:electron`，`pnpm dev` 先切 Electron，`pnpm test` / `pnpm dev:web` 先切回 Node（取的都是预编译包，秒级）；主进程启动失败对话框识别到 ABI 错误时直接给出修复命令（`apps/desktop/startup-error.js`，测试 `test/startup-error.test.js`，打包版不显示该提示）。顺带踩到并修了一个打包坑：`@electron/rebuild` 在 `build/Release/.forge-meta` 记“已按 Electron 编过”，而 prebuild-install 换回 Node 二进制时不动这个标记，`pnpm deploy` 把标记一起拷进 `.stage` 后 electron-builder 就跳过重编，打出来的包启动即报 ABI 不符（本机实测一次）。`native-abi.mjs node` 现在会删掉标记，`pack-desktop.mjs` 也会在 `.stage` 里清一遍再打包。
3. 缓存 4/5 命中：根因在 `packages/core/src/plan.rs` 的 clip 排序——同一开始时间、同一时长的 clip 以 id 决定次序，而 AIGC 水印 clip（`packages/local/src/export/aigc.js`）的 id 每次导出都是新 UUID，次序一变场景键就变。改为按 clip 内容（去掉 id 后的规范化 JSON）决定并列次序；测试 `tie_breaking_ignores_clip_ids`。用新 lycore 对同一时间线、不同水印 id 各计划一次，5 个场景键完全一致。注意排序规则变了，升级后旧缓存首次全部失效（一次性重渲）。打包版二次导出复验见下。
4. 数据目录不可自定义：已加 `apps/desktop/user-data.js`，支持启动参数 `--user-data-dir=<绝对路径>` 和环境变量 `TALEKILN_USER_DATA_DIR`（参数优先，只认绝对路径，去掉首尾引号），覆盖时写一行 main.log；测试 `apps/desktop/test/user-data.test.js`。开发态用环境变量实跑验证数据落到指定目录；打包版用启动参数直接指到“中文 目录	alekiln”复验见下（不再需要目录联接）。
5. ffmpeg 无 libx264：固定版 LGPL ffmpeg 带的是 `libopenh264`。`encoder.rs` 候选表加 `libopenh264`（software，排在 libx264 之后）；`render.rs` 给它 `-b:v 8M`，回退顺序改为硬件在前、软件在后（`order_fallbacks`）；导出页编码器文案加“软件编码 (libopenh264)”。测试：`openh264_is_the_software_fallback_when_libx264_is_absent`、`fallback_order_keeps_software_last`、`exportJob.test.js`。所以没有硬件编码器的机器现在回退到 libopenh264，而不是只剩 h264_mf。打包版 encoder.detect 复验见下。

### 问题 1：`timeout: encoder.detect`（产品侧潜在 bug，已修）

- 现象：exportE2E / bailianE2E 里导出前的编码器检测报 `timeout: encoder.detect`。
- 根因：lycore 客户端 `connect()` 给所有 RPC 一个统一的 5 秒超时；而 `encoder.detect` 要按候选表顺序对 7 个编码器各做一次 ffmpeg 试编码，每个探测 lycore 自带 15 秒超时，空闲机器实测约 3 秒，机器忙（并行跑测试、或用户机器后台占满）时轻易超过 5 秒。这不是测试环境问题：打包版里导出页的 `GET /export/options` 和「开始导出」走同一条路，用户机器忙时会直接报错。
- 修法：客户端 `call(method, params, { timeoutMs })` 支持按调用放宽超时（默认值不变），导出服务给 `encoder.detect` 单独 120 秒（7 × 15 秒 + 列表）。桌面主进程经 `coreProvider` 的 facade 原样转发参数，无需改动。
- 测试：`packages/core/client/timeout.test.js`（本地假服务器，验证默认超时、按调用放宽 / 收紧、正常回包不受影响，已加进 core 包的 test 脚本）；`export.test.js` 新增用例断言导出服务传给 `encoder.detect` 的超时 ≥ 60 秒。

### 问题 2：kernelCompat.test.js 的 ECONNRESET（测试夹具问题，已修）

- 现象：`kernelCompat.test.js` 偶发 `fetch failed` / ECONNRESET，单跑 24/24。
- 排查：先怀疑纯 CPU 争抢，起 16 个占 CPU 的进程单跑它仍能过，排除；再给 socket 加跟踪，发现 undici 的连接池给这个服务开了两条 keep-alive 连接并交替使用，测试辅助函数在两次请求之间做大量同步快照比对，一条连接空闲超过 Node http 服务默认的 5 秒 `keepAliveTimeout`；客户端与服务端在同一个被拖慢的事件循环里，服务端过期的 keep-alive 定时器与客户端复用该连接的写入落在同一轮，请求写到了一条正在被销毁的连接上。
- 产品不受影响：Electron 渲染进程（Chromium）对复用连接被重置会自动重发，且桌面端前后端不在同一个进程里。
- 修法：测试里 `app.listen` 之后 `server.keepAliveTimeout = 0`，每个请求用新连接，并注明原因。
- 待产品 / 基建决定（未改）：本地测试里起 express 服务的夹具不止这一处，如果以后别的测试文件也出现同类偶发，可以考虑抽一个公共的测试服务器 helper 统一关 keep-alive，或者把服务端 keepAliveTimeout 调高；本次只改了出问题的这一处。
